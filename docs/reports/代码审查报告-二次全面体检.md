## 一、确定性缺陷

### 1. RealBasicVSR / SeedVR2 输出偏色 🔴

**现象**：用 5 个已知颜色的色块（BT.709 编码，和相机、剪辑软件的输出一致）分别跑三条处理链路，再按播放器的方式解码回 RGB，和原色比较：

| 链路 | 最大偏差 | 红 (200,40,40) | 绿 (40,170,60) | 肤色 (224,172,140) |
|---|---|---|---|---|
| 源文件本身 | 3 | (199,39,40) | (37,168,59) | (223,171,139) |
| Lanczos | 3 | 与源一致 | 与源一致 | 与源一致 |
| ncnn（Real-ESRGAN） | 5 | (198,38,37) | (42,174,65) | (225,173,139) |
| **PyTorch 引擎管道** | **22** | **(212,53,38)** | **(26,148,54)** | (226,172,135) |

红色偏橙偏艳，绿色明显发暗，灰色不受影响。这是典型的 BT.601 和 BT.709 矩阵错配。

**原因**：编码命令（`worker.py:528-533`、`seedvr2_runner.py:256-261`）把 `rgb24` 转成 `yuv420p` 时没有指定矩阵，FFmpeg 默认用 BT.601，而且输出文件**没有打色彩标签**。播放器遇到没有标签的高清视频，会按 BT.709 解码，于是偏色。

ncnn 链路（`src/conversions.cpp`）其实也没指定矩阵，但它解码和编码两头都用 601，一来一回互相抵消，所以只有很小的偏差。

**改法（已验证）**：编码命令里加上

```
-vf scale=out_color_matrix=bt709:out_range=tv
-colorspace bt709 -color_primaries bt709 -color_trc bt709 -color_range tv
```

验证结果：高清源的偏差从 **22 降到 4**；标清 480p 源（无论有没有 601 标签）放大 2 倍后，偏差从 **22 降到 5**。标清源在解码时 FFmpeg 会正确按 601 处理，所以编码端统一输出 709 就是对的。

### 2. 可变帧率源在默认设置下音画不同步 🔴

**现象**：构造一段 60 秒的可变帧率视频（标称 30fps，每 6 帧丢 1 帧，平均 25fps，和手机拍摄的特征一样），每一帧的画面里都编码进源帧号，然后逐帧检查"输出时间戳"和"画面实际对应的源时刻"是否一致：

| 处理器 | 重算时间戳 | 音画偏差 | 输出视频时长 |
|---|---|---|---|
| Lanczos ×2 | **开（默认）** | **最多 −10.00 秒** | 49.97 秒 |
| Lanczos ×2 | 关 | 0.00 秒 | 59.97 秒 |
| Real-ESRGAN ×2 | **开（默认）** | **最多 −10.00 秒** | 49.97 秒 |
| Real-ESRGAN ×2 | 关 | 0.00 秒 | 59.97 秒 |

默认设置下，60 秒的视频画面会短 10 秒，播放速度变快，越往后和声音差得越多。按这个比例，一小时的手机视频会差 10 分钟。

**原因**：`src/libvideo2x.cpp:271` 和 `src/encoder.cpp:354` 用"帧序号 ÷ 帧率"重写每一帧的时间戳，帧率取自解码器的标称值（30fps）。可变帧率源实际帧数更少，按 30fps 排时间戳，整体就被压缩了。界面上这个开关写的是"修正输出 PTS（建议开）"（`EncoderSection.tsx:92`），默认值是 `true`（`args.ts:211`）。

**影响范围**：你本机现有的 6 个素材全部是恒定帧率，**目前不受影响**。手机拍摄和录屏的视频基本都是可变帧率，以后处理这类素材就会碰上。恒定帧率源在两种设置下都完全同步。

**改法**：不能简单把默认值改成"关"，因为关掉后 RIFE 会崩溃（见第 3 条）。正确做法是**收敛时间戳的处理**：不插帧的处理器保留源时间戳（只做时基换算），只在插帧或源没有时间戳时才重算。这也是以前报告第 7 条里建议的"时间戳所有权收敛到一处"。

### 3. RIFE + 关闭重算时间戳 → 程序崩溃，输出损坏 🔴

**现象**：恒定帧率和可变帧率的源都能稳定复现，退出码 139（段错误），输出文件损坏，无法打开（"moov atom not found"）。

```
[error] Application provided invalid, non monotonically increasing dts to muxer in stream 0: 131072 >= 1024
[critical] Error encoding/writing frame: Invalid argument
[critical] Video processing failed with error code -22
Segmentation fault
```

**原因**：这就是以前报告里的第 7 条。`interpolator_rife.cpp:137` 给插值帧赋时间戳时没有考虑 `time_step`，插值帧和原帧共用同一个时间戳，muxer 拒收。以前的判断是"播放器行为未定义"，**实际后果是直接崩溃**。

同时还暴露出另一个独立的问题（第 12 条）：报错之后，程序在清理阶段段错误。正常情况应该是报错退出，并保留可诊断的信息。

**改法**：和第 2 条一起改。插值帧的时间戳应该是 `原帧时间戳 + time_step × 帧间隔`。在修好之前，可以先在界面上做限制：选 RIFE 时，"重算时间戳"强制打开且不能修改。

### 4. PyTorch 引擎处理可变帧率源时周期性跳帧 🟠

**现象**：按 `worker.py` 的真实逻辑模拟（每段 240 帧，从 `seg_start-8` 开始 seek，丢掉前 8 帧当上下文，最后分片拼接）：

| 源 | 音画偏差 | 画面跳变 |
|---|---|---|
| 恒定 30fps | 0.00 秒 | 0 处 |
| 可变帧率（平均 25fps） | 最多 **+1.66 秒** | **6 处**，例：输出第 240 帧从源 7.97 秒跳到 9.53 秒 |

在每个 240 帧的分段里，画面会越走越慢于声音，到分段边界再突然往前跳 1.6 秒，大约每 10 秒发生一次。

**原因**：帧率取的是 `avg_frame_rate`（25，`worker.py:201`），但解码到 rawvideo 时，FFmpeg 会按标称的 30fps 补齐重复帧。两边的帧号对不上：seek 按 25fps 换算，而读出的帧是按 30fps 排的。

**改法（已验证）**：解码命令（`worker.py:524`、`seedvr2_runner.py:252`）里加上 `-vf fps=<平均帧率>`。验证结果：音画偏差在 **−0.03 到 +0.05 秒**之间，**没有跳变**。

### 5. 分几次提交、输出同名的任务互相覆盖 🟠

**复现**：用真实的 `POST /api/jobs` 接口，对同一个输入和同一个输出路径连续提交 3 次：

```
第 1 次提交（如 nomos8k）→ 输出 116_v2x.mp4
第 2 次提交（如 SPAN）  → 输出 116_v2x.mp4
第 3 次提交            → 输出 116_v2x.mp4
```

任务是串行执行的，后跑完的会直接覆盖先跑完的。拿同一个视频对比不同模型时，正好会碰上这种情况。默认的命名模板 `{name}_v2x.{ext}` 不包含处理器名，所以换了模型输出名也不变。

**原因**：`bridge.mjs:1081` 的 `dedupeOutPath` 只处理两种情况：同一次提交里重名，以及磁盘上已经存在的文件。排队中的任务还没生成文件，所以检测不到。

**连带问题**：PyTorch 引擎的断点文件是按输出路径命名的（`<输出>.v2xckpt.json`）。如果前一个任务暂停了，后一个同名但参数不同的任务开跑时，会因为指纹不一致执行"清理旧分片"（`worker.py:486`），**前一个任务的续跑进度就没了**。

**改法**：去重时把排队中、运行中、已暂停任务的 `outPath` 也算进去，改动不大。可以再考虑把默认命名模板改成带处理器名的形式，比如 `{name}_{proc}.{ext}`。

---

### 6. 断点指纹里没有 `bit_rate`（上轮引入）🟡

上一轮我给 PyTorch 引擎加了 `--bit-rate`，但没同步加进断点指纹（`worker.py:456`、`seedvr2_runner.py:129`），指纹里只有 `crf`。如果一个任务中途暂停，改了码率再续跑，新旧分片会用不同的码率控制方式编码，然后拼进同一个文件。

**改法**：两个指纹里各加一行 `'bitRate': args.bit_rate`。

### 7. 过期文案（上轮引入）🟡

`NewJobView.tsx:295` 写着 PyTorch 引擎下"码率 / 像素格式 / AVOption / 流复制开关不适用"，但码率现在已经支持了，应该把"码率"从这句话里删掉。

## 二、健壮性与可诊断性（另一台电脑事故暴露）

### 8. 打包时可能静默生成空壳包 🟠

electron-builder 碰到不存在的 `extraFiles` 源目录时，只打一条 **debug 级别**的日志（`appFileCopier.js:114` "skipped copying"），正常打包时看不到，也不会报错。

而 `video2x.exe`、Python 运行时、权重、`models/`、`ffmpeg-shared` **都不在 git 里**（已逐项确认）。所以，在另一台电脑上 clone 代码再运行 `npm run dist`，会顺利得到一个只有 Electron 外壳的包，就是那台电脑上看到的症状。

**改法**：加一个 `predist` 脚本，打包前检查关键文件是否存在（video2x.exe、python.exe、各个权重、models），缺任何一个就直接报错退出。打包后再检查一次输出目录的文件数和大小。

### 9. 找不到根目录时静默回退，界面提示有误导 🟠

那次事故的完整链条：

1. `findProjectRoot`（`bridge.mjs:20`）找不到 video2x.exe，**静默回退**到 `resources\`
2. 标题栏两个引擎都显示红点，但"开始处理"按钮变灰时（`NewJobView.tsx:123`），**界面上没有任何原因说明**
3. 资源横幅显示"缺少组件 → 立即下载"，可缺的其实是整个程序文件，下载解决不了
4. 下载 RealBasicVSR 权重后，`verifyCheckpoint`（`bridge.mjs:287`）调用 `python.exe` 做加载校验。python.exe 不存在会报 ENOENT，被当成"校验失败"，于是把**刚下载好的权重删掉了**

**改法**：

- 回退到 `resources\` 时，`/api/health` 返回一个明确的"程序文件不完整"状态，界面显示为红色错误条，并列出缺少的文件
- 按钮不可用时，在按钮旁边写出原因：引擎未就绪、缺权重、分辨率无效等
- `verifyCheckpoint` 要区分"Python 不存在"和"权重损坏"，前者不能删文件

### 10. 没有日志文件 🟡

任务日志只存在内存里（最多 400 行），落盘到 `cache/jobs.json` 时只保留每个任务的最后 100 行。bridge 自己的 `console.log` 在 GUI 模式下直接丢弃。程序一关，排障信息就没了。

**改法**：写入 `cache/logs/bridge-YYYYMMDD.log`，同时镜像 `console` 输出和各任务的 stdout，保留最近 7 天，约 30 行代码。

### 11. 嵌入式 Python 里 10 个包的元数据重复 🟡

`site-packages` 里有 10 个包同时存在两份 `.dist-info`：

| 包 | 实际在用 | 残留元数据 |
|---|---|---|
| torch | 2.11.0+cu128 | 2.13.0 |
| transformers | 4.46.2 | 5.14.1 |
| diffusers | 0.33.1 | 0.39.0 |
| huggingface_hub | 0.36.2 | 1.25.1 |
| tokenizers | 0.20.3 | 0.22.2 |
| filelock / fsspec / tqdm / setuptools / typing_extensions | — | 各有一份 |

时间线：7 月 28 日 18:19 装过一批新版本，20:07 又降回了旧版，但新版本的元数据目录没删干净。

**已核实运行时是干净的**：实际文件和旧版本的 RECORD 清单 **100% 吻合**（torch 全部 11,653 个文件、transformers 1,846 个、diffusers 602 个），新版本也没有残留文件。`pip check` 无冲突。

**隐患**：SeedVR2 会经由 diffusers 加载 transformers，而 transformers 4.46.2 要求 `huggingface-hub<1.0`、`tokenizers<0.21`。现在之所以正常，是因为 NTFS 的目录顺序恰好让旧版本的元数据排在前面。另外，如果以后要装 SageAttention 之类的包，pip 有可能按错误的清单卸载文件。

**改法**：删掉这 10 个残留的 `.dist-info` 目录（只是元数据，不涉及代码文件）。**这一步必须在执行任何 pip 操作之前完成。**

### 12. 处理中途出错时程序崩溃 🟡

第 3 条里，报错后程序没有正常退出，而是段错误（退出码 139）。说明处理过程中只要出现错误，程序就可能崩溃，同时留下损坏的输出文件。这可能和以前报告里暂缓的第 25 条（错误路径上的 AVFrame 泄漏）有关，建议一起排查。

## 五、可以更新和优化的地方

### 依赖更新

| 依赖 | 当前 | 建议 |
|---|---|---|
| Electron | 43.2.0 | **升级到 43.7.7**（同一大版本的补丁，包含 Chromium 安全修复） |
| React / Vite 等 | 19.2.3 / 7.3.0 | 同一大版本的补丁可以顺手升级 |

| `@hookform/resolvers` / `date-fns` / `zod` | 未被引用 | 都是 shadcn 模板的残留，打包时会被摇树掉，删除的收益几乎为零 |

上游 video2x 自 6.4.0（2025 年 1 月）之后没有新版本，SeedVR2 也没有出新模型（上一轮已查过）。

### 功能优化

1. **文件日志**（第 10 条）：排障的基础，优先做
2. **默认命名模板带上处理器名**：和第 5 条互补，对比模型时更方便
3. **SeedVR2 加速**：vendor 代码已支持 `attention_mode`（sageattn_2/3、flash_attn）和 `torch.compile`，但 runner 里写死了 `'sdpa'`。**前提是先完成第 11 条的清理**
4. **多显卡并行**（以前报告第 19 条）：每张卡一个任务槽
5. **评估 SwiftVR**：2026 年 6 月发布的生成式视频修复模型，速度大约是 SeedVR2 的 22 倍。但需要大显存，16 GB 能不能跑还没有验证
6. **PyTorch 引擎**：目前不保留字幕流，也只支持 8-bit 输出，可以考虑补上
