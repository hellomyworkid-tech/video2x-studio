### ✅ 第 8 条 CORS 写侧 CSRF

`bridge.mjs:1015-1019`：

```js
// CSRF 写侧拦截：CORS 头只挡"读响应"，挡不住请求送达（text/plain 简单请求无预检），
// 非本机来源的 /api/* 必须在路由前直接 403；无 Origin（Electron 同源/curl）放行
if (origin && !res.corsOrigin && url.pathname.startsWith('/api/')) {
    return send(res, 403, { error: 'Forbidden: cross-origin request rejected' });
}
```

四个关键点全部正确：

| 检查项 | 结论 |
|---|---|
| **拦截位置** | 在 `try` 块和所有路由匹配**之前**，任何副作用都到不了 |
| **拦截范围** | 仅 `/api/*`；静态文件服务（第 1570 行往后）不受影响，Electron 加载页面正常 |
| **放行条件** | `origin &&` 前置 —— 无 Origin 头的请求放行。Electron 同源导航、`curl`、本地脚本均不受影响 |
| **本机白名单** | 复用 `res.corsOrigin`，`127.0.0.1` / `localhost` / `[::1]` + 任意端口，vite dev（3000）可用 |

上轮指出的攻击路径（evil.com 用 `text/plain` 简单请求驱动 `POST /api/jobs`、`/api/jobs/N/delete`、`/api/jobs/cancel-pending`）现在会在路由前被 403 挡住，副作用不再发生。

顺带确认：第 1002 行注释里的 "vite dev 为 localhost:7100" 已改正为 `localhost:3000`，与 `vite.config.ts` 一致。

### 残留 ②：显存策略仍按 0 号卡决策 🟡

`seedvr2_runner.py:56-63`：

```python
def pick_memory_strategy():          # ← 不接收 device 参数
    try:
        import torch
        total_gb = torch.cuda.get_device_properties(0).total_memory / (1 << 30)
                                                     # ↑ 硬编码 0
```

而调用点 `mem = pick_memory_strategy()`（第 102 行）在 `dev` 之前，也没传设备。

**后果（仅限异构多卡）**：0 号卡 8GB、1 号卡 24GB 的机器上选 1 号卡，会读到 8GB 从而套用 `total_gb < 12` 分支 —— `blocks=16`（激进 BlockSwap）+ `conv3d_wa=True`（cuDNN 绕路，注释自述 **VAE 慢 3–5 倍**）+ `tile=512`。24GB 卡被强制跑最保守的低显存策略，性能损失显著。

同卡型多卡（最常见的多卡配置）不受影响。

**修法**：`pick_memory_strategy(dev)`，内部 `torch.cuda.get_device_properties(dev)`；把 `mem = ...` 挪到 `dev` 计算之后。

### 残留 ③：全程没有 `torch.cuda.set_device()` 🟡

全仓库（`worker.py` + 三个 runner）搜索 `set_device`：**零命中**。

`torch.cuda.empty_cache()` 作用于 PyTorch 的**当前设备**，而当前设备在未调用 `set_device` 时恒为 0。三处调用点因此都在清 0 号卡的缓存：

| 位置 | 调用 |
|---|---|
| `worker.py:306` | `torch.cuda.empty_cache()` — 分块推理每块结束后 |
| `flashvsr_runner.py:229` | 每段推理后 |
| `seedvr2_runner.py:330` | 每子段解码后 |

跑 `cuda:1` 时，这些调用对 1 号卡不起作用 → 长任务下 1 号卡的分配器缓存持续累积，正是这几处 `empty_cache` 原本要防的碎片化问题。（`worker.py:41` 设的 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 能缓解但不能替代。）

同理，`torch.autocast('cuda', ...)`（worker.py:273/290）用的是 device **type** 不带索引，本身正确，但它作用于当前设备上下文 —— 在 set_device 缺失时语义同样模糊。

**修法**（一行，三个引擎全受益）：`worker.py` 拿到 `device` 之后立即

```python
if use_cuda:
    torch.cuda.set_device(device)
```

由于两个 runner 都由 `worker.py` 分发进入（`main()` 内 `from vsr_models.X import main`，同进程），在 worker 里设一次即可对三条链路全部生效。
