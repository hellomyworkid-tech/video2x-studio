# macOS（Apple Silicon）SwiftVR 实测报告

> 日期：2026-10-09
> 硬件：Mac Studio，Apple M5 Max（32 核 GPU）/ 36 GB 统一内存 / macOS 27.0.1
> 软件：PyTorch 2.14.1（MPS）、Python 3.12.15、Homebrew ffmpeg@7 7.1.5
> 对照：Windows 11 + RTX 5070 Ti 16 GB（数据来自 `docs/macos/04-knowledge-handoff.md` 与 `testdata/reference-windows/`）
> 测试素材：`testdata/inputs/` 的 A（1280×720，72 帧）、B（854×480，72 帧）、A20（1280×720，480 帧）

## 结论

- **SwiftVR 能在 Mac 上出片，画质与 Windows 一致。** 与 Windows 参考输出逐帧比，平均 PSNR 44.3～44.7 dB，和 Windows 上同配置重跑两次的编码噪声（约 45.8 dB）同一量级。
- **2K 稳态约 3 fps，约为 Windows 的 40%～45%。** Windows 上开 FP8 计算是 7.1 fps，bf16 计算是 5.7 fps。
- **短片段的总耗时 Mac 反而更短。** 模型加载 10～18 s，也没有 cuDNN 首次调优（Windows 约 20 s）。例如 72 帧 2K：Mac 41 s，Windows 50 s。
- **36 GB 跑 2K 内存偏紧。** 峰值约 26～29 GB，跑 480 帧时系统换页增加了约 0.9 GB，换出的是其他程序的内存。渲染 2K 时建议少开别的大程序。
- **慢在算力，不在实现。** DiT 占每步耗时的 86%，主要是大矩阵乘。M5 Max 的 bf16 矩阵乘约 47 TFLOPS，5070 Ti 约 90（FP8 再翻倍），MPS 上也没有 FP8 计算可用。

## 速度

稳态速度去掉了模型加载和首步预热，由带时间戳的进度行计算。

| 输出 | 分段 | Mac M5 Max 稳态 | Windows 5070 Ti 稳态 |
|---|---|---|---|
| 2560×1440（A，72 帧） | 8 | 3.16 fps | 7.1 fps（FP8 计算）；5.7 fps（bf16 计算） |
| 2560×1440（A20，480 帧，两个宏分片） | 8 | 2.94 fps | — |
| 1708×960（B，72 帧） | 16 | 6.9 fps | — |

| 一次性开销 | Mac | Windows |
|---|---|---|
| 模型加载 | 10～18 s（官方 FP32 → bf16） | 5～9 s（FP8 文件） |
| 首步（含预热） | 约 3～4 s | cuDNN 自动调优约 20 s |
| 72 帧 2K 总耗时（含加载） | 41 s | 50 s |

每步各阶段耗时（2K，分段 8，取 6 步）：

| 阶段 | 耗时占比 |
|---|---|
| 预处理 + VAE 编码 | 2% |
| DiT | 86% |
| VAE 解码 | 12% |

## 内存

| 输出 | 分段 | MPS 峰值（driver_allocated，含缓存） | 进程峰值（time -l） |
|---|---|---|---|
| 2560×1440 | 4 | 19.1 GB | — |
| 2560×1440 | 8（默认） | 25.9 GB | 26.4～29.2 GB |
| 2560×1440 | 12 | 超出 28.1 GB 上限，报 OOM | — |
| 1708×960 | 4 / 8 / 16（默认） | 15.3 / 17.7 / 23.7 GB | 23.5 GB |

- bf16 权重常驻 9.4 GB（QKV 融合后删掉了原始投影层）。
- PyTorch 的 MPS 上限设为 `recommended_max_memory` 的 1.0 倍（本机 28.1 GB），超出即报 OOM，按分段减半重试。实测强制 `--clip-len 24`：依次退到 12、8 后完成，没有陷入换页。

## 分段长度：为什么不为省内存改小

在 Mac 上分段长度几乎不影响速度：2K 分段 4 是 3.14 fps，分段 8 是 3.09 fps；960p 分段 4 是 7.30 fps，分段 16 是 7.14 fps。分段 4 还能少占 7～8 GB 内存，看起来是更好的选择。

但分段长度就是 DiT 每次联合处理的时间跨度（分段 ÷ 4 个潜空间帧）。runner 设 `dit_overlap=0`，分段之间没有重叠，所以分段 4 时 DiT 每次只看 1 个潜空间帧。有真值的对照实验（A20 前 96 帧作真值，缩到 640×360 并 CRF 28 压缩后放大回 1280×720）：

| 分段 | 与真值 PSNR | 帧间闪烁（输出与真值相邻帧差之差，越小越稳） |
|---|---|---|
| 4 | 26.84 dB | 3.51 |
| 8 | 27.33 dB | 3.20 |
| 16 | 27.45 dB | 3.16 |
| 24 | 27.47 dB | 3.14 |
| （双三次基线） | 33.60 dB | 1.83 |

- 分段 4 的保真度和帧间稳定性都明显更差，8 以上差别很小。
- 局限：PSNR 是保真度指标，生成式模型会补细节，所以绝对值低于双三次基线（见 `短剧素材选型实测报告.md` 的勘误）。这里只做同一模型不同分段的横向对比，帧间闪烁更能说明问题。
- 结论：Mac 沿用 Windows 的分段表（2K 用 8，1080p 级用 16，更小用 24）。输出与 Windows 一致，速度不受影响。

## 正确性验证

| 项目 | 结果 |
|---|---|
| `B_swiftvr` 与 Windows 参考 | 平均 44.66 dB，最低 43.07 dB，通过（阈值 38 / 32） |
| `A_swiftvr_2k` 与 Windows 参考 | 平均 44.26 dB，最低 37.97 dB（第 72 帧，Windows 上末尾几帧本来就偏低），通过 |
| A20 480 帧，跨两个宏分片 | 输出 480 帧、2560×1440。缩回输入尺寸逐帧比：第 240 帧前后连续（33.8～34.8 dB）；故意错一帧的对照只有 30.75 dB |
| 断点续跑 | 第 253 帧时 `kill -9`（检查点在 240）；无残留进程；重启从 240 续跑，结果与不中断运行逐位相同 |
| MPS 回退 CPU | 无（未设 `PYTORCH_ENABLE_MPS_FALLBACK`）。唯一的警告是"超过 3 维的常数填充走 View Ops 实现"，仍在 GPU 上执行 |

## 已知问题与后续

- vendor 的 `streaming/dit.py` 在 RoPE 缓存需要扩展时，会在设备上建 float64 张量（MPS 不支持）。只有单个流式会话超过 1024 个潜空间帧时才触发；runner 每 240 帧新开会话，用不到。
- 24 GB 机型的退路：FP8 权重以 uint8 常驻 MPS、前向查表还原。实测还原与 CPU 逐位一致，线性层慢约 30%，权重内存减半（约 5 GB）。尚未接入。
- 界面说明与预检估算还是 RTX 5070 Ti 的数据，阶段 2 改界面时按本报告补 Mac 数据。
